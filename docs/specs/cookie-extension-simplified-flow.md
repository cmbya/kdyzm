# 登录同步插件：简化流程与本地升级需求

状态：需求和Apple风格界面稿已由用户于2026-11-05确认，并授权同步Figma后继续实现。插件1.2.0实现与验收中；后台维持3.1.20、App维持3.1.22。设计来源见[可交互原型](../designs/cookie-sync-apple/index.html)和[Figma交付记录](../designs/cookie-sync-apple/figma-handoff.md)。发布事实以发行记录为准。

## 目标与范围

保留“绑定后台”和“反向授权”两种入口，复用后台地址、平台选择、身份核对、同步结果与登录补救。日常首页只显示连接情况、角色与平台状态、主要操作。用户已选择继续本地版，简化覆盖更新，不上Chrome商店。

本次不做平台自动输入密码、自动处理验证码、跨Chrome配置提取登录、自动替换另一账号、安装常驻本机服务、配置企业浏览器策略或商店发布。已有后台和账号协议优先复用；发现必须更改公开契约时再说明具体变化。

## 当前问题与依据

- 两份后台地址与浏览器名称输入，完整授权表单长期占首页：cookie-extension/options.html。
- 无独立的最近后台地址设置，只有待处理反向申请会回填地址：options.mjs的setPendingRequest。
- 反向申请在family.mjs的startRequest中逐平台读取，任何平台缺登录都会终止整份申请；后台申请接口本身只接收名称和平台清单，并不要求提交Cookie。
- 单个平台长期并列登录、读取、同步、自动同步；角色批量按钮又重复部分操作。
- 目前发布的是解压加载源码包，manifest没有固定key；同一原目录覆盖并重新加载可升级，每版另建目录再加载可能变为另一扩展实例。不能把新版本号误当作必须新增安装。

## 本地升级

1. 提供一个本地更新入口，首次由用户选择当前Chrome已加载的插件目录，保存该路径。已有用户不自动搬家、不新增扩展、不修改现有扩展标识；新用户使用不含版本号的固定目录。
2. 后续双击更新工具，显示当前版、目标版和目标目录；从既有可信发行来源取得插件包，验证版本、文件清单和摘要后覆盖。无更新则结束。
3. 下载与解压使用临时目录；拒绝目录穿越、路径逃逸和非插件目标。只替换插件文件，保留前一版本文件备份；失败恢复原文件，不删除Chrome配置或导出配对令牌。
4. 覆盖完成后，用户点击插件设置中的“重新加载”，或Chrome扩展管理页的重新加载按钮。不自动操作用户浏览器、开启远程调试或降低系统策略。
5. 更新前提示结束正在进行的同步；重载前检查当前同步状态，避免把进行中的任务提示为完成。升级保留后台地址、角色授权、平台选择和自动同步设置。
6. 插件设置中收纳“当前版本 / 检查更新 / 获取更新工具 / 重新加载”。纯插件按钮不承诺静默运行本机更新工具，首个过渡版本可使用Chrome扩展管理页重载。
7. 发布插件版本时保持App Latest和App更新索引不变。更新工具不把任意后台返回的执行文件作为可信安装源；具体插件发布清单复用既有仓库并在实现时校验。

这是“更新工具覆盖 + 重新加载”的本地升级，不是商店式静默更新。Chrome普通Windows环境对商店外打包扩展的分发有限制，添加update_url不能让当前解压加载方式自动升级。

## 页面组织

首页顶部为后台地址摘要、连接状态和设置入口。未配置时只展开一次地址输入；保存后记住，后续授权自动使用。地址格式合法但暂不可达时仍保存输入，保留原配对，显示暂不可达；不误报未绑定。

首页主体是角色卡片：角色名称、平台状态、最后同步时间，“同步所选平台”作为主要操作，“管理平台”作为次要操作。已有多个后台时按后台隔离显示，可切换，不把不同后台或角色合并。单一后台隐藏无用的切换控件。

添加授权时提供两个入口：

- 绑定后台：使用后台生成的配对信息或配对码。
- 反向授权：从插件发起，让后台批准并选择角色。

初次进入直接展示这两个选择；已有连接时收纳在“添加授权”内。一次只展开一个流程，原有两个大表单不常驻首页。帮助、版本、浏览器名称、诊断、撤销授权收纳到设置或更多操作。

结构示意（不是批准的视觉稿）：

```text
登录同步                         设置
后台：已连接 · 已保存地址

角色：家人A
淘宝    已同步        最近时间
京东    已同步        最近时间
拼多多  需要登录      [去登录]

[同步所选平台]  [管理平台]
自动同步：已开启2个平台

[添加授权]
  绑定后台 / 反向授权
```

## 两种授权流程

### 绑定后台

保存或复用后台地址 → 粘贴配对信息 → 读取并展示目标角色 → 打开统一平台选择弹窗 → 选择平台并检查 → 核对新账号并确认同步 → 汇总结果，突出待处理项。

- 配对信息包含地址时自动解析；若与已保存地址不同，先明确提示目标后台，用户确认后使用，不静默转移已有授权。
- 弹窗顶部显示后台和目标角色，下方仅展示淘宝、京东、拼多多选择及状态。不为未选平台申请权限或读取Cookie。
- 首次不替用户选择平台；后续编辑回显原选择。目标核对与平台选择在一个连续引导中完成，不来回跳页。
- 旧单账号配对码自动识别，在同一个入口接受，只展示其实际授权平台，不升级成角色级权限。

### 反向授权

复用后台地址 → 同一平台选择弹窗 → 请求访问权限并检查各平台 → 发起授权申请 → 自动打开后台选择/新增角色并批准 → 插件显示批准的角色 → 进入同一账号核对与同步流程。

- 选择平台后可发起申请，某个平台没登录不再阻止整个申请；缺登录的平台保留为待处理。申请仅传浏览器名称和平台清单，批准前不保存平台Cookie或创建账号。
- 等待批准只展示一个进度区域：“等待后台授权”，附“打开后台”和“取消”；授权码放在展开详情中。
- 插件重新打开仍可恢复有效的待处理申请；过期后仅提示重新发起，不清除已保存地址或其他角色。
- 后台批准必须仍由管理员明确选择角色。回到插件后展示获批角色，避免默认猜测家人归属。

## 共用同步与登录补救

1. 只检查本次选择的平台，每个平台独立出结果。检查Cookie结构只能说明读到了必要字段；后台采集成功才代表实际会话可用。
2. 已核对过的同一账号直接同步，无须再经过预览确认。首次账号、首次新增平台仅在同一弹窗集中显示脱敏账号与目标角色，保留一次“确认同步”。首次核对不能因自动化而省略。
3. 结果汇总为“已同步N个平台，M个平台待处理”。成功项先完成，不因另一平台未登录或失败而回滚，也不重复要求登录成功项。
4. 对缺登录的平台，在同一结果弹窗中显示“去登录”；不连续弹多个对话框、不自动打开所有平台网页。用户点击才打开对应官方登录页，支持在同一Chrome配置中使用DevTools平板模拟。
5. 登录期间保留本次后台、角色和平台目标。Cookie变化或用户返回插件时自动重新检查待处理平台，进行防抖和并发去重；已有身份一致则继续本次同步，首次识别账号集中提示确认。取消流程、切换目标或撤销授权后，旧检测不得上传。
6. 登录检测没有结果时保留“重新检查”入口；不承诺读取Cookie成功等于登录已被平台认证。
7. “本次同步”和“后续自动同步”分开：前者是用户当前操作，后者用一个清楚的可选设置启用，默认关闭。首页只显示自动同步汇总，逐平台开关收在“管理平台”；旧用户的不同平台开关原样保留。
8. 浏览器休眠/关闭时不承诺自动同步；Cookie过期、验证码或扫码仍由用户处理。新增后台账号仍默认未选择，不继承其他账号的同步开关。

## 按状态提供下一步

| 状态 | 首页/结果展示 | 操作 |
| --- | --- | --- |
| 同步完成，采集尚未验证 | 已同步，等待采集验证 | 无需重复登录 |
| 缺少登录、后台已确认过期 | 需要登录 | 去登录 |
| 未授予站点权限 | 需要授权 | 授权并继续 |
| 后台不可达或请求超时 | 连接失败，保留历史状态 | 重试 |
| 浏览器账号与绑定账号不同 | 账号不匹配，已停止 | 查看账号并切换登录；不自动覆盖 |
| 多个同平台账号无法确定目标 | 选择要同步的账号 | 明确选择，不同时覆盖不同身份 |
| 配对撤销或过期 | 授权已失效 | 重新授权 |
| 页面需要验证码/扫码 | 需要完成平台登录 | 打开平台，由用户完成 |

技术错误码、Cookie字段诊断默认折叠；展开或复制诊断只含脱敏信息。常驻页面不展示授权Token、原始Cookie、管理员密码或订单内容。

## 合并项和约束

| 当前重复项 | 统一后的入口 |
| --- | --- |
| 两处后台地址、两处浏览器名称 | 共用后台设置；浏览器名称自动默认，可在设置修改 |
| 单项读取、批量读取、立即同步常驻 | 首页统一同步操作；新账号确认按需出现 |
| 每个平台常驻登录按钮 | 仅待登录平台显示 |
| 页面上多处分散的平台选择、自动开关 | 统一管理平台弹窗，首页显示汇总 |
| 一直展示配对表单和反向申请表单 | 添加授权时选一种方式，按步骤展开 |
| 全局刷新和角色刷新 | 状态自动刷新，失败处重试；高级操作保留必要手动刷新 |
| 旧单账号独立大区块 | 同一角色列表展示，标注实际授权范围 |

保存后台地址不代表已授予角色权限。更换地址不迁移授权令牌，不把旧Cookie发往新后台。账号身份校验、首次确认、凭据版本冲突保护、授权撤销及异步取消检查必须保留；不通过布局重构放宽后台校验。

## 验收与验证策略

1. 旧插件在原目录升级后Chrome仍只有原实例，地址、角色、平台选择和自动同步设置保留；异常安装包/中断可恢复，不碰App发布入口。
2. 新用户只输入一次后台地址；重开插件仍回显。已有用户从授权记录恢复默认地址，不丢多个后台。
3. 两种授权方式最终使用同一平台选择、首次确认与结果组件；同一角色的重复授权按现有撤权语义明确处理，不静默生成重复角色卡。
4. 三平台中两项已登录、一项未登录时，两项可先同步，未登录项单独显示登录入口；反向申请不因其未登录被整体挡住。
5. 登录回来后无需重填地址、重新配对或重选平台；身份已确认则自动继续，未知/不同身份不自动覆盖。
6. 拒绝权限、取消申请、撤销、切换角色、网络失败及重复点击均不能产生未经选择的读取或错误目标上传。
7. 首页无重复大表单，390px与桌面均无横向溢出；键盘可操作，弹窗焦点和关闭行为正确；错误处有准确下一步。
8. 保留本次已修复的PDD HTTP/HTTPS Cookie权限和JD light_key兼容。用实际隔离Chrome、合成Cookie和临时后台验证，覆盖自动流程、首次确认和部分失败。
9. 相关单测、授权与竞态回归、必要的独立安全审查、项目要求的完整门禁及旧版本升级实测通过后再交付；真实账号验证区分登录信息已保存和后台采集成功。

确认记录：用户已确认本文件整体流程及页面组织，并指定“苹果科技风、简洁”的新界面方向。升级渠道已选定本地覆盖方案；不再重复询问商店选择。权限变更与真实首次账号确认继续由用户在产品内完成，不新增无意义的开发审批步骤。
