# 分平台物流读取准确度优化

日期：2026-11-10。任务：TASK-087。本地代码与验证；尚未发布或部署。

## 证据与范围

本轮分别检查京东 PC 买家接口、拼多多订单／拆包／柜码接口、淘宝 SSR／PC 完整物流。使用既有脱敏真实响应、已有协议测试和重新读取的官方页面脚本；新增失败场景使用隔离合成数据，未调用真实账号刷新或修改生产订单。不能将合成回归通过表述为线上准确率测量。

- 京东使用既有已验证的 `pcorder_center_list`、`pcdetail_traceMultiPackage` 结构，详见 `jd-warehouse-3.1.10.md` 和 `server/test/jd-collector.test.mjs`。
- [淘宝官方物流脚本](https://g.alicdn.com/code/npm/@ali/mtb-logistics-v2/1.0.46/js/p_h5-detail-index.js)显示：空 `richContent` 回退到 `text`；切换包裹提供 `mailNo/cpCode/orderCode`，SSR 服务端读取这些参数。既有真实已取样本位于 `server/fixtures/taobao-collected.json`。
- [拼多多物流页](https://mobile.yangkeduo.com/goods_express.html)当前引用的[官方脚本](https://static.pddpic.com/assets/js/react_goods_express_ce1d6aa9d2183a0a7ff4.js)确认拆包列表、逐包轨迹和柜码查询相互独立。逐包柜码仅在平台跳转链接明确 `external=1` 时，使用已返回的 `shipping_id/tracking_number/entry_source`。

## 最终行为

| 平台 | 修复与优化 |
| --- | --- |
| 京东 | 仅部分子包签收、另一个活动子包缺失时，不再写整单已签收；最新催取提醒无码时，从同包当前取件周期内恢复有效码，遇签收、退回、改投、重新派送停止回溯。 |
| 拼多多 | 柜码、主轨迹及分包响应校验所有已支持的订单／运单身份别名；单笔刷新补查柜码，明确外部分包按自己的参数获取柜码；分包列表或柜码失败保留已验证轨迹，可重试错误先保存成功部分。 |
| 淘宝 | 空富文本回退正文，忽略空节点，去除重复包裹描述；主运单未出现在不完整分包列表中时仍保留，明确不同运单的详情不附着；缺独立详情的分包使用官方选择参数补查并核对返回运单。 |

三个平台均保留未来／时间矛盾的原始轨迹用于诊断，但不让它们覆盖可信的当前物流状态；自动领取依据也必须通过显示时间与时间戳的一致性检查。不依据当前年份、抓取时间或订单消失补造物流事实。

同时间、同正文但平台状态矛盾的事件，在采集、数据库和客户端均保留为独立事实，兼容字段和真正重复项仍合并。100条历史限额按同键事件组处理，服务端优先保留最新和未知时间的完成反证，避免丢失待取证据后继续沿用旧的已取结论。

淘宝已确认的“包裹已从代收点取出”仅从当前 `doing` 变为历史 `done` 时，若事件时间、正文、标签、状态文字、地点和子状态完全一致，不撤销原领取事实；首次只见 `done` 仍不能新触发自动领取。否定、更晚待取、人工恢复待取等守卫保持有效。
