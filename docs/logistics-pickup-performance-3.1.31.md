# 物流领取识别与同步优化

配套版本：后台 3.1.31，App 3.1.35 / 30135。

## 已确认的原因

拼多多物流正文可能一直写“代收点凭码领取”，但实际接口已把节点从 `IN_CABINET / 待取件` 更新成 `OUT_CABINET / 已取件 / OUT_CABINET_501`。旧适配器只保留正文和时间，丢掉这组结构化状态，导致无法自动确认领取。此次通过用户当前登录会话只读核对了截图订单的接口；没有点击平台确认收货或修改生产数据。

另一个漏判来自全文关键词过滤：明确“本人签收”的正文附有“如有疑问请联系快递员”，客服话术被当成领取主体或不确定性。现在只忽略独立且不包含物流动作的联系信息，保留否定、失败、退回及纠错检查。

## 修复行为

- 采集、数据库、快照、客户端和领取证据都保留平台节点来源、状态、标签、子状态及展示文字；原始物流说明不改写。
- 仅已核实的 `pdd + OUT_CABINET + 已取件 + OUT_CABINET_501` 组合进入自动领取判断。无有效时间、未来时间、较新入柜/退回、明确失败或用户人工撤销均不能被覆盖。通用“已签收”仍不等于本人已领取。
- 节点按时间、说明及位置去重，已有旧节点补全新字段，不把不同位置或冲突状态混合成新证据。
- 自动领取更新已绑定取件项，保留短信与包裹关联、原取件码及撤销入口；不向购物平台确认收货。后台监测记录展示“平台已取件”规则与实际命中。
- 更新后台后，下一次成功采集才会补齐旧记录缺失的字段；只有旧正文时不推测已领取。

## 同步耗时

拼多多柜码/物流以及淘宝独立物流 GET 阶段每账号最多同时发起 2 个请求，保留每批预算、最旧优先、失效中止和在途收尾。淘宝会话协商、日期请求及京东共享 Cookie 流程保持串行。正常请求总数不增加，平台冷却与限流不变。

客户端直接使用快照中的任务状态，省掉重复的逐任务请求和第二次快照；快照裁剪、旧后台、304、重新绑定均保留兼容处理。非冷却任务首次轮询从 1500ms 缩短至 300ms，后续仍为 1500ms。

同一脱敏 10 单 fixture、每次请求注入约 10ms 延迟的测量：拼多多约 366→204ms，淘宝约 535→381ms，京东约 173→174ms；请求数分别仍为 22、34、11。合成任务在 100ms 完成时，前台在 300ms 可见，原先为 1500ms。这些是受控测试，不代表真实平台或手机能固定在某个秒数内完成。AI 网络请求仍在独立队列，明确平台证据无需等待模型返回。

## 大卡片

“待发货 / 运输中”及数量汇总移到“待收包裹”标题下。订单行统一平台、商品、家人三列，保留无障碍状态说明；覆盖多平台、筛选、分页、隐私、空列表和放大字体。

NAS 由用户自行更新镜像并保留数据卷、密钥及绑定。没有执行真机安装、真实短信后台调度或启动器验收；没有以本次测试替代 nightly / Semgrep 安全检查。

最终完整门禁：590 项 App、564 项镜像后台、236 项 Android 测试通过；密钥扫描、H5 构建、原生打包和 lint 通过（0 errors / 59 warnings）。新增回归覆盖原始接口至数据库/HTTP/客户端、自动领取不解绑、人工恢复、不同地点轨迹保留及并发错误收尾。
