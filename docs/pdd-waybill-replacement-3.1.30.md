# 拼多多运单变更整理（服务端 3.1.30）

2026-11-07 核对后台 SQLite 与拼多多原始物流后发现：N35 是一个订单下保留了旧圆通发货预报和当前申通运单，并非两个订单父项。当前平台显示一个申通包裹。此前的同运单去重无法处理两个不同的运单号；普通更新会保留未返回的旧记录，因此反复刷新不能清理这一实例。

另一个已确认问题是采集器将 `cabinet.companyName`（代收点名称）用作承运商。现在只从运单列表或运单号严格匹配的物流详情 `shippingName/shipping_name` 取承运商。仅拼多多、明确站点后缀、同订单同运单且候选唯一的历史记录允许原位纠正，保留原 ID、取件码及操作历史。真实不同承运商、不同分包键和歧义候选继续保持隔离。

## 核实后整理一个运单变更

此工具不推断“平台只返回一个运单就是单包”，不自动处理其他不同运单。先人工核对账号、订单号、原始物流、分包状态以及新旧运单，再预览：

```sh
node scripts/confirm-shipment-replacement.mjs \
  --database /data/pickcode.db \
  --oldId OLD_SHIPMENT_ID --targetId CURRENT_SHIPMENT_ID \
  --orderNumber PLATFORM_ORDER_NUMBER \
  --evidence '已核对平台当前运单及无分包；旧运单仅发货预报'
```

默认只读。输出旧运单、当前运单、保留取件码、领取周期和确认摘要。经实际数据变更授权后，用相同参数追加 `--confirm PREVIEW_CONFIRMATION` 执行。

执行会在写锁内重新核实相关订单、包裹、物流和身份记录的摘要；先生成仅当前用户可读的 SQLite 备份，再增加一条历史别名并提升同步版本。原订单、两条原包裹记录、短信和领取状态不删除、不更改；手机同步后只显示当前包裹，旧身份及绑定按既有别名协议收敛。不会向购物平台确认收货。

人工领取/隐藏/删除、已有操作或别名、旧运单已到站、多次投递周期、不同分包键，以及预览后的证据变化都会阻止执行。失败时事务回滚。备份在数据库同目录，包含原数据库隐私数据，不应上传仓库或对外分享。需要撤销时应审查并撤销本次别名、提升同步版本；不要直接用全库备份覆盖仍在更新的生产数据库。

验证覆盖：真实模式的“旧圆通预报→当前申通”重现；短信绑定、人工站点、身份历史保留；再次刷新不复活旧记录；证据变化拒绝旧确认；备份、事务回滚和并发写入保护。手机无需更换 3.1.33 APK。
