# kdyzm · 私人取件助手服务端

为私人取件助手提供线上订单、运单和取件码同步，推荐配套App 3.1.3，兼容旧版设备协议。Node 24 + SQLite，单容器运行，无需 Redis 或外部数据库。

源码：https://github.com/zsdd2/kdyzm

镜像：`ghcr.io/zsdd2/kdyzm:latest`（Linux amd64 / arm64）；本次版本为 `3.1.3`，也可固定使用 `ghcr.io/zsdd2/kdyzm:3.1.3`。

## 直接拉取部署

需要 Docker Engine + Compose v2。**新部署不需要提前配置 PUBLIC_BASE_URL、ADMIN_TOKEN、COOKIE_ENCRYPTION_KEY，也不需要创建 `.env`。** 管理员密码和服务地址在首次打开页面时设置，加密密钥由服务自动生成并保存在数据卷。

1. 新建目录并下载完整 Compose：

```sh
mkdir -p kdyzm
cd kdyzm
curl -fL https://raw.githubusercontent.com/zsdd2/kdyzm/main/compose.yaml -o compose.yaml
```

2. 拉取并启动，不需要克隆或编译源码：

```sh
docker compose config --quiet
docker compose up -d --pull always
docker compose ps
curl -f http://127.0.0.1:8787/health
```

健康接口正常返回 `{"ok":true}` 表示服务已启动，不代表已完成初始化。

3. 在 NAS / Docker 管理器查看此容器日志，或运行：

```sh
docker compose logs kdyzm
```

找到 `KDYZM_SETUP_CODE=…`，等号后面是自动生成的**一次性初始化码**。它用来防止后台尚未设置时被其他人抢先初始化，不是需要你提前生成的密钥；初始化完成后不能再使用。不要把这段日志公开。

4. 在可信内网打开 `http://服务器内网IP:8787`，按首次设置页面填写：

| 页面项 | 填写方式 |
| --- | --- |
| 一次性初始化码 | 粘贴容器日志中 `KDYZM_SETUP_CODE=` 后的内容 |
| 管理员密码 / 确认密码 | 自己设置12–128字符密码，以后用它登录后台 |
| HTTPS服务地址 | 例如 `https://kd.example.com`，不包含路径；尚未配置域名可先留空 |

提交完成后进入登录页。Cookie加密密钥自动保存，无需填写、复制或在界面中显示。配置和数据库都持久保存在 `/data`；重启和升级不会重置密码或密钥。

如果尚未填写HTTPS服务地址，可以先登录管理账号；生成App绑定码前，到「服务设置」填写。后续也可在设置中修改管理员密码，旧管理会话会立即失效。

飞牛 / Portainer 等管理界面可以直接粘贴 [compose.yaml](compose.yaml) 创建项目，保留数据卷，然后按上述日志和首访步骤操作。端口冲突时只需修改主机端口（映射冒号中间的8787），容器内部端口仍为8787。

## HTTPS与访问地址

网页首次设置可以通过可信内网完成；**App绑定仍要求HTTPS地址**。填写地址不会自动创建域名、申请证书或开启HTTPS，需要使用已有反向代理。

默认监听主机 `0.0.0.0:8787` 方便内网首次访问，不要将明文8787端口映射公网。同机HTTPS反向代理转发到 `127.0.0.1:8787`；代理在另一台设备或容器网络时，转发到可达的主机内网地址，并用防火墙限定访问。代理保留原始 `Host`、`Authorization`、`If-None-Match`、`ETag`，不记录认证头、Cookie或请求体。

可以通过可选 `.env` 设置 `BIND_ADDRESS=127.0.0.1` 限制为同机代理访问，或设置 `PORT=其他端口`；这些不是初始化密钥。

同机 Caddy 的最小站点配置示例：

```caddyfile
parcel.example.com {
    reverse_proxy 127.0.0.1:8787
}
```

本 Compose 不代替现有代理、域名解析或证书配置，也不自动启动模拟订单。

## 后台和 App 绑定

1. 浏览器打开后台，使用首次设置的管理员密码登录。准备绑定App时，确保「服务设置」中的HTTPS地址已经可访问。
2. 添加本人淘宝或拼多多账号及 Cookie，点击“立即采集”。默认每小时采集，可改为30分钟。Cookie 加密保存，不发送给 App。
3. 选择允许同步的账号，生成十分钟一次性绑定码或二维码。
4. App 的「我的 → 线上账号」填写同一 HTTPS 地址和绑定码。二维码可由系统识别后粘贴到 App。
5. 账号 Cookie 过期只需在后台更新；设备被撤销后需重新绑定。后台可以单独撤销设备。

淘宝使用本人 `taobao.com` 登录态 Cookie；拼多多使用 `mobile.yangkeduo.com`，需包含 `PDDAccessToken` 和 `pdd_user_id` 或 `pdduid`。不要把 Cookie、管理员 token 或加密密钥发到 Issue、提交或截图中。

## 数据与刷新

- 订单先进入包裹记录；到站且有码才进入取件列表。普通签收、退款或列表缺席不代表助手已取。
- 淘宝沿用原项目的待发货、待收货筛选，补充物流暂不可用时保留有效订单；拼多多沿用未收货范围。新发现的结束或无关订单不导入，已有记录只更新状态且保留历史；已有未取运单仍可更新最新物流。筛选摘要显示在账号同步提示中，不依赖商品标题黑名单。
- 真实下单日期缺失时标记未知，首次同步时间独立保存；旧版数据的日期来源待确认，获取真实日期后补正。App按实际状态显示暂无物流、待发货、运输中或到站待取码，历史记录可展开查看。
- 一单多运单独立保存，不确定哪个包裹对应取件码时保留无码，避免随意复制。
- 服务端约每小时采集；App 前台读取已有快照，后台约每小时同步；不是平台实时推送。
- 领取、恢复、隐藏等助手操作按设备和操作ID去重，离线可重放；不会在电商平台确认收货。
- 短信解析和关联在手机本地完成，短信正文不上行。
- Cookie AES-256-GCM 加密；设备token和绑定码仅hash落库；每个设备只能读取授权账号。

API见 [PROTOCOL.md](PROTOCOL.md)。

## 持久化、升级与备份

数据在命名卷 `kdyzm_kdyzm-data` 的 `/data` 内，包含SQLite数据库和 `service-config.json`（密码hash及Cookie加密密钥）。容器删除重建不会删除该卷；不要执行 `docker compose down -v`，也不要删除配置文件来重置密码。

Compose 默认使用 `latest` 和 `pull_policy: always`。每次执行 `docker compose up -d --pull always`（或管理器中的重新部署/构建）都会检查镜像仓库，拉取通过CI验收的主分支最新镜像；无需手动修改版本号。普通 `docker restart`、`docker compose restart`、`docker compose start` 只启动现有容器，不拉取新版本。管理器若有“拉取最新镜像”选项，请启用；上述CLI命令可显式保证拉取。

`latest` 与 `edge` 跟随每次成功的 `main` 构建，版本标签（如 `3.1.2`）用于固定部署或回退。发布旧版本标签不会覆盖 `latest`。这不是后台定时自动升级，正在运行的容器只在你重新部署时更新。必须保留完整数据卷，丢失其中的加密密钥会导致旧Cookie无法解密。一个数据卷只供一个服务实例使用。

3.1.3在有效订单筛选和人工状态保护的基础上，补查淘宝订单详情中明确标注的创建/下单时间，并保存淘宝、拼多多逐运单物流轨迹。App展开包裹或取件详情即可查看已同步轨迹。详情日期可纠正旧列表日期，失败和空响应保留已有轨迹；普通签收不会自动标记助手已取。

日期补查每轮最多10笔、同单失败后间隔至少24小时；物流补充每轮最多20笔并优先较久未补查的活跃运单。单运单最多保存最近100个节点，大快照按手机响应上限裁剪本次输出，数据库缓存保留。缺少完整事件时间时显示平台原时间文本。

平台接口仍依赖有效Cookie和平台是否返回数据。拼多多日期使用订单列表的真实时间字段；其订单详情需要额外平台签名，本服务不伪造签名，列表缺日期时仍显示待确认。数据缺失不拿同步时间代替。服务端升级不会更新手机资源，需要覆盖安装App 3.1.3；保留数据目录及原应用数据。

备份时先 `docker compose stop`，备份完整命名卷及自定义部署配置，然后 `docker compose start`。SQLite包含WAL文件，不能只复制运行中的单个 `.db`。备份含加密密钥，应限制读取权限；恢复先在隔离环境验证，再切换正式服务。

### 已使用3.1.0环境变量部署的用户

保留原 `.env` 中的 `PUBLIC_BASE_URL`、`ADMIN_TOKEN`、`COOKIE_ENCRYPTION_KEY` 和原数据卷，再更新镜像。新Compose会继续透传这些值，以旧环境变量模式运行；登录页面输入原 `ADMIN_TOKEN`，设置页显示由部署环境管理。不要删掉旧密钥后尝试重新初始化，这会使旧Cookie无法解密；程序会拒绝在已有数据库缺少密钥时生成新密钥。首次设置模式与旧环境变量模式不能混用。

## 开发和镜像构建

```sh
npm ci
npm test
docker build -t kdyzm:smoke .
node scripts/docker-smoke.mjs kdyzm:smoke
```

Node需要24.13.0或更新版本；内建SQLite可能显示实验特性提示。CI先跑业务、认证、首次设置和采集器mock测试，再检查无密钥环境变量启动、首访设置、非root容器、只读根目录、API认证及重启持久化，最后构建并推送amd64/arm64镜像。主分支发布`latest`和`edge`，版本标签`v3.1.3`发布`3.1.3`；所有构建均带`sha-提交号`标签。非main分支手动构建不会覆盖`latest`或`edge`。CI使用GitHub提供的临时token，不需要在仓库保存发布密钥。

`npm run fixture`仅供本机临时模拟，监听127.0.0.1:8787，数据保存在内存且不联系电商平台。正式镜像不含fixture脚本或测试数据。

## 已知边界与许可

淘宝/PDD采集依赖登录态网页接口，并非官方公开查件API。平台可能修改字段、限制请求或要求验证；真实账号采集、平台风控及目标主机的HTTPS仍需部署者验收。历史暂无自动清理，大量历史积累时需另行设计分页，当前App单次响应上限2MiB。
